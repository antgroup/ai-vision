## Assessment

AI Vision already has useful foundations: canonical compact projections, selected list fields, capacity/admission guards, paged worker transport, explicit completeness and unknown states, and collapsible JSON. The main architectural gap is the **detail data path**: whole-Trace download, full Span-derived models and selected-Span access still share a complete-Trace assumption. Local capacity work makes some failures more local but does not replace that assumption.

The largest directly evidenced gaps versus Langfuse's current path and LangSmith's public APIs are metadata-first topology, independently selected content, and explicit representation-specific limits. A different class of work belongs only to our proposed target: stable as-of catalog history and a complete browser ownership ledger. Public competitor evidence does not prove equivalent implementations, so these cannot honestly be scored as competitor leads.

## How the OceanBase foundation changes the design

The comparison above describes application data paths, not an absence of database capability. AI Vision already uses OceanBase-specific typed SQL, relational keys, source locking, revision CAS and read-only repeatable-read snapshots. The [OceanBase execution profile](../research/oceanbase-execution-profile-20261107.md) makes those foundations explicit instead of treating every competitor storage pattern as something to reproduce.

| OceanBase foundation | Selected use in the revised design | What remains to implement/qualify |
|---|---|---|
| Same-store SQL transactions and exact row locks | Commit raw/current catalog/index/revision and reversible contributions together; keep optional rich derivation outside the critical write transaction. Reuse existing source fences. | New current catalog/index and maintenance-independent tracking; concurrency/replay tests. Database atomicity does not implement per-Trace transaction partitioning for us. |
| Scoped B-tree and covering indexes | Narrow rowstore catalog and topology, typed scalar filter/order keys, exact selected Span/body lookup. Avoid another full-window core scan or whole-Trace payload download. | Query/index schema and actual plan/work proof. The important competitor gap is reading granularity and readiness, not acquiring a new analytics database. |
| Native MVCC/flashback | Prefer a qualified same-point native J1 profile over an application-maintained history duplicate/global publication epoch. | Verify exact package support, minimally privileged point acquisition, cross-table/page snapshots, retained history cost, GC/DDL and expiry. Retain journal fallback only for a profile that needs it. |
| Row/column/hybrid storage and supported aggregates | Use rowstore for interactive current state; evaluate compact column/hybrid analytical facts within the same foundation. | Exact version/BP, optimizer and write-amplification qualification; preserve canonical unknown/root/ownership rules. No measured latency benefit is claimed. |
| Native governance and application pools | Isolate ingestion, interactive reads, projection and export using actual session limits/pools and qualified resource groups where supported. | Real enforcement/cancellation/noisy-neighbor tests; seekdb has its own capabilities. Space is not automatically a separate database tenant. |

This can reduce additional infrastructure and custom history-maintenance work, especially if native snapshots qualify. It does not remove the selected-content API, sparse UI models, byte/structure budgets or isolation tests. The native history cost can include a larger tenant workload, so it is not assumed cheaper than a compact journal. No new universal minimum CE/seekdb version or Oracle/Enterprise dependency is introduced.

## Delivery priorities and risk

1. **R1 first: the missing detail architecture.** Deliver one compact-list → bounded header/topology → explicitly selected content/refusal flow, using the current database, canonical rules and writer fences. Start with a bounded single pane, not shared retained content. This closes the most visible and directly evidenced competitor gap.
2. **W1 in its own patch set:** preflight, byte packing, Trace-local transactions, immutable accepted values on rejection and catalog tracking independent of rich maintenance. Real mixed A/oversized-G/B storage outcomes matter more than the presence of an error DTO.
3. **A1 as a separate compatibility cutover:** decide and qualify actual terminal receipts/durability, Pi's short sender timeout, retries, backpressure and lost responses. Current queued acceptance cannot be relabeled durable commit. R1/W1 do not automatically deliver this wire contract.
4. **J1/C1/B1/X1 by explicit capability:** qualify native catalog snapshots before implementing application history, then add larger content ranges, multi-view/cache ownership and each consumer only with their own gates. A live-keyset first delivery must expose live semantics; it cannot promise stable as-of completeness.

R1 is a medium-to-high integration risk because authorization, canonical semantics, writer/index coverage and full-array UI assumptions cross components. W1/A1 are high-risk write/transport changes. The additive approach and independent gates make risk containable; competitor examples do not prove that our chosen defaults or compatibility are qualified. No justified percentage-complete or calendar estimate follows from this source assessment.

Measure Linux and browser peak/retained memory, decode/layout work, actual returned bytes/query plans, and end-to-end mixed-item outcomes before claiming capacity. We have no comparable Langfuse/LangSmith benchmark, so storage technology, request ceilings and commercial deployment scale are not used as performance rankings.

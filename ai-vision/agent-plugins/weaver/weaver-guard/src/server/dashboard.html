AiVision API 文档
用于 agent 或脚本读取最近语义问题，并清理本地 dashboard 诊断数据。

        

          
          
        

      

      

        

          
1. 获取 violations / findings

          
GET /api/violations

          
返回最近诊断中的 finding 列表。默认只返回 violation，默认最多 10 条；响应同时提供 findings 和兼容字段 violations。

          

            
Query说明示例

            
              
limit返回条数，默认 10，最大 100。limit=10

              
signal按信号过滤：traces / events / metrics；也兼容 span/log 等别名。signal=events

              
level按等级过滤：violation / improvement / information / semconv；支持逗号分隔。level=violation,improvement

              
levelslevel 的复数别名；也支持 all。levels=all

              
include_payload是否返回原始 payload；默认 false，避免接口默认暴露 prompt/tool payload。include_payload=true

            
          

          
curl 'http://127.0.0.1:4319/api/violations?limit=10'
curl 'http://127.0.0.1:4319/api/violations?signal=events&level=violation,improvement&limit=20'
curl 'http://127.0.0.1:4319/api/violations?levels=all&include_payload=true&limit=5'

          
兼容历史拼写：/api/voilations 也会路由到同一个接口；新脚本应使用 /api/violations。

        


        

          
2. 清理本地诊断数据

          
POST / DELETE /api/clear

          
清空当前进程内保存的 recent diagnostics、findings 和 payload 记录。不会删除 Rego 规则、semconv 文件，也不会清理 Jaeger/Victoria 后端数据。

          
curl -X POST 'http://127.0.0.1:4319/api/clear'
curl -X DELETE 'http://127.0.0.1:4319/api/clear'

          
响应示例：

          
{
  "cleared_records": 12,
  "remaining_records": 0,
  "scope": "recent_diagnostics"
}

AiVision 接入/修复指南
新项目先用 Bootstrap 接入，本地上报后用语义修正 Loop 校验、诊断和修复，再转发到本地观测后端。

        

          
          
        

      

      

        

          
1. 作用

          
本地语义校验网关

          
AiVision 作为本地 OTLP HTTP 接收端，接收 agent 上报的 traces、events/logs 和 metrics，加载 Rego 规则与语义约定后生成 diagnostics，并把通过策略允许的数据写入本地 Jaeger / Victoria 后端。

          
    
            
  • 实时发现缺字段、废弃字段、非法枚举、span/event/metric 结构问题。
    • 
            
  • 在页面中查看最近上报、命中规则、完整 payload 和修复 prompt。
    • 
            
  • 顶级按信号类型切换：Traces / Events / Metrics；每个信号内部再查看 Overview、Findings、Diagnostics、语义约束与 Payloads。
    • 
            
  • 语义约束来自 Rego 注释，支持按 policy group（默认 aivision）单独展示和启用/关闭。
    • 
            
  • 默认转发策略为 Always：即使存在 violation，也保留样本方便排查。
    • 
          

        


        

          
2. 接入配置

          
把 agent 的 OTLP endpoint 指向 AiVision

          
    
            
  1. 启动本地服务：make -C weaver serve。
    2. 
            
  2. 新项目或新 agent 优先点击 AI 工作流，在"新项目接入"标签页选择接入等级和信号类型后复制 prompt 给 AI 完成第一版上报。
    3. 
            
  3. 将 agent 的 OTLP HTTP endpoint 改为 AiVision 地址，默认：http://127.0.0.1:4319。
    4. 
            
  4. 按信号上报到标准路径：/v1/traces、/v1/logs、/v1/metrics。
    5. 
            
  5. 回到本页面查看 Traces / Events / Metrics 的 Overview、Diagnostics、Findings 和 Payloads。
    6. 
          

          
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4319
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
# 或按信号分别配置：
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://127.0.0.1:4319/v1/traces
OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=http://127.0.0.1:4319/v1/logs
OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://127.0.0.1:4319/v1/metrics

        


        

          
3. 语义出现问题后的操作

          
复制问题上下文，让 AI 修上报或规则

          
    
            
  1. 已有真实上报后，优先点击 AI 工作流，切换到"语义修正"标签页，选择修复等级和确认策略，复制 prompt 给 AI 执行 validate / clear / re-report 循环。
    2. 
            
  2. 进入对应信号的 Findings 或 Diagnostics，点击 诊断。
    3. 
            
  3. 如果是上报缺字段/字段名错误，选择 Trace / instrumentation bug，复制 AI Prompt 交给 AI 修改 agent 上报逻辑。
    4. 
            
  4. 如果怀疑规则误报，选择 Rule / semconv bug，复制 rule prompt 给 AI 修改 Rego 规则和测试样例。
    5. 
            
  5. 需要完整证据时，点击 复制 Prompt + Payload 或打开 Payload modal 复制原始上报。
    6. 
          

        


        

          
4. 忽略语义

          
只在确认是预期偏差时忽略

          
如果某个 finding 是兼容期、灰度期或特定 agent 的预期偏差，可以临时忽略，但建议保留原因和范围，避免全局关闭重要规则。

          
    
            
  • 单次诊断：在 Finding modal 选择 Expected exception，复制例外说明给 AI 生成有范围的 suppression/说明。
    • 
            
  • 规则开关：进入 语义约束，优先关闭单条规则；必要时再关闭规则组。
    • 
            
  • 继续写入后端：Forward 策略保持 Always，可以让不合规样本仍进入 Jaeger / Victoria 便于对比。
    • 
            
  • 长期忽略：应在规则注释、README 或报告中记录 owner、原因、过期时间和恢复条件。

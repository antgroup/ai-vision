# 从一组 Trace 开始诊断

在当前 Space 选择自己的 Agent，进入「观测 → Agent 轨迹」。在列表中勾选轨迹，或打开一条轨迹的详情，点击「运行诊断」。诊断使用已有诊断器和已保存的专项检查，结果可在「诊断 → 质量看板」回查。此操作不会重新执行 Agent。

诊断需要可读取的 SigNoz Trace；只有 Langfuse 数据源时，不提供运行入口。

## 选择轨迹和诊断器

1. 在轨迹列表中选择 1–10 条实际 Trace，也可以从详情直接运行当前 Trace。运行窗口显示已选 ID，不再查询另一份候选列表。
2. 选择一个已配置的诊断器或专项检查。规则沿用已保存的判断条件；LLM 诊断器沿用已保存的模型连接，不在此处覆盖模型或提示词。
3. 配置不完整或模型不可用的项不能运行。通过「管理诊断器与专项检查」在新标签页中完成配置，然后回来「刷新诊断器」。创建和编辑权限沿用诊断器页面的规则。
4. 点击「运行诊断」。服务端固定本次配置，创建独立批次并保存结果，无需手动创建 Dataset 或 Job。

规则检查（Rule）直接检查已记录的事件和结果，例如修改后是否观察到有效验证。语义检查（Core）使用模型核对当前请求、回应和有来源的材料，例如文本是否满足要求、回答是否有资料支持。

代码检查中的「实际交付检查」需要实际执行或产物材料；对话检查描述的是文本要求满足情况。阅读所选检查的材料要求和判断范围，避免把回答中的成功声明当作执行证据。

「执行声明核对」将最终报告中的声明与已记录事件核对。例如报告写「`test_app.py` 通过」，可关联唯一一条 `python3 -m unittest test_app.py -v` 这样的单文件命令，路径必须完全相同。重复执行或语法不支持且没有其他明确对应材料时，只将该 Trace 的本项检查标为未判定，不代表通过，也不影响其他检查；具体边界见[通用 Core](../../../agentlens/docs/diagnoser/llm/general-core.md)。

页面显示「正在准备」时，会继续确认同一次检查。连接中断后，使用「恢复这次请求」继续确认结果；无需连续创建新检查。若页面提示请求冲突或原条件不可用，先阅读原因，再明确调整选择。

## 读懂发现、依据和覆盖

先看本批次的状态，再看记录中的具体发现和判断理由。运行信号描述工具失败、循环或风险等事实，不能直接说明任务完成质量。只有质量检查参与质量分数；没有质量检查、材料不足、执行失败或覆盖不完整时，分数可能不可用。

| 页面显示 | 如何理解 |
|---|---|
| 0 分 | 本批可评分的质量检查通过比例为 0；这是检查结果，不表示诊断服务执行失败。 |
| 100 分 | 本批可评分的质量检查通过比例为 100%；只描述这些样本和所选检查，不代表整个 Agent 的准确率。 |
| 不可用或 `—`（接口中的 `null`） | 当前材料或覆盖不足以形成完整质量分数，或只运行了信号检查；不能当作 0 分。 |
| 未判定（SKIP） | 该项检查无法作出判断，例如材料缺失；不是通过，也不能用于证明问题已修复。 |

覆盖说明分别列出扫描和选定的 Trace 数、有效检查次数、未判定和执行失败次数。一个 Trace 可以对应多个检查，因此检查次数不能当作 Trace 数。未判定不是通过，也不一定产生诊断记录；页面会解释实际记录的原因，例如材料不足、隐私遮蔽或额度耗尽。当前筛选没有记录，也不表示整批检查通过。

有「查看来源步骤」时，打开原始 Trace 并核对该步骤。未记录来源步骤，或当前 Trace 中找不到该步骤时，页面会明确说明；可以继续查看完整 Trace。历史记录显示当时固定的检查定义，无法读取原定义时不会用当前检查名称代替。

模型请求观测中的额度占用不代表服务方已经收到请求。响应未确认或 Token 总量未知时，不能视为零消耗；部分已观测用量仅覆盖页面标明的请求范围，也不是完整账单。

## 确认线索并采取下一步

查看原始步骤、输入输出和运行背景，判断发现是否成立。具备反馈权限时，可以提交「确认」「误报」或「无法判断」及备注。已确认或误报的记录不可再次修改；「同步中」表示还在等待回读，不能当作反馈已展示完成。反馈说明人的判断，不改变历史检查结果，也不能证明应用已经修复。

对于质量问题，回到自己的 Agent 应用修改实现，再用相同输入重新执行；保留新产生的 Trace。对于运行信号，先确认它是否影响任务，再决定是否需要修改应用。诊断执行失败时，先检查执行消息和材料。

## 使用新 Trace 验证修改

回到自己的 Agent 应用修改实现并重新执行，然后在轨迹列表或详情中对新 Trace 运行同一诊断器。每次新运行使用该诊断器**当前保存的配置**；修改过配置的批次不能宣称条件完全相同。已生成的批次保留原始配置和结果，之后编辑诊断器不会改写历史判断。

「再次运行」也会创建新批次。对旧 Trace 重跑只能重新判断已记录的执行，不能证明应用中的修改已生效。分数提高、未发现问题或人工确认都只能提供观测线索，还需在应用中用独立测试核实。

历史结果链接继续可用。按固定批次查看记录时，顶部时间范围不参与筛选，因此可以查看早于默认 7 天窗口的结果；数据仍受服务端保留期限制。旧版运行接口和其已有冻结条件元数据保留兼容，但不再提供独立的快速检查入口。

## 权限和能力边界

可执行的诊断器、模型连接和反馈均由当前服务端权限及 Agent 绑定决定。权限或本人绑定变化后，旧结果会被清除并停止刷新。小样本诊断只描述所选检查在这些样本上的判断，不能代表整个 Agent 的表现。

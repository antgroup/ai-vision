# Future Helm deployment contract

Helm support is a committed follow-up for AI Vision. **No product Chart, Helm
installation command or Helm deployment target is available today.** Issue #88
records the boundaries for that delivery; it does not implement, package or
publish a Chart. The current supported Kubernetes entry point remains
`aiv cast --target kubernetes`, using OB Operator-managed OceanBase CE.

The future path must retain the same reviewed product semantics as
[`base/`](https://github.com/antgroup/ai-vision/tree/main/deploy/kubernetes/base),
the [lifecycle/resource contract](lifecycle.md) and
[component identities](https://github.com/antgroup/ai-vision/blob/main/deploy/components.json).
Chart rendering, dependency packaging and hook choices will be decided during
implementation. Do not create a second set of speculative templates now.
Helm planning does not add seekdb, external database, HA or native v1 history
configuration support to today's Kubernetes path.

## Configuration mapping

The proposed value areas below are design boundaries, **not accepted CLI keys
or an implemented `values.yaml` schema**. Exact names and validation belong to
the future Chart. Current inputs are defined in the [configuration reference](README.md#configuration).

| Current source or input | Future value area | Compatibility requirement |
| --- | --- | --- |
| `--namespace`, kubeconfig context; local state keyed by cluster UID and namespace | Release namespace and installation identity | Preserve namespace, resource names and Service DNS when adopting an installation. A different release name must not silently create a second database or metastore |
| `IMAGE_REGISTRY`, `IMAGE_TAG`, `IMAGE_PULL` | Shared image defaults and pull policy | Resolve and record the exact per-role image references; app tag changes do not update database or controller images |
| `DATA_BACKEND_IMAGE` / `SIGNOZ_IMAGE`, `INGEST_GATEWAY_IMAGE` / `GATEWAY_IMAGE`, `BACKEND_IMAGE` / `BE_IMAGE`, `DIAGNOSIS_IMAGE` / `AGENTLENS_IMAGE`, `FRONTEND_IMAGE` / `FE_IMAGE` | Image override for each canonical role | Retain upstream repository names deliberately; normalize existing aliases when converting configuration |
| `DATABASE_IMAGE` / `OB_IMAGE`, pinned `dependencies/` and `INGRESS_IMAGE` | Database and dependency image/version selection | Preserve the database image guard and compatible-controller checks; a Chart update alone cannot upgrade an existing database |
| `IMAGE_AUTH`, `IMAGE_PULL_SECRET`; `AIV_GHCR_*` used by the CLI | Existing image pull Secret references | Do not require CLI login or store registry tokens in public values, examples or logs |
| `PUBLIC_HOST`, `PUBLIC_PORT`, `PUBLIC_SCHEME` | One public Web/OTLP HTTP origin | Derive CORS, CSRF, cookies and advertised endpoints from the same origin; preserve proxy trust rules and existing internal ports |
| `INGRESS_CONTROLLER`, `INGRESS_CLASS`, `INGRESS_HTTP_NODE_PORT`, `INGRESS_HTTPS_NODE_PORT`, `INGRESS_TLS_SECRET` | Managed/existing Ingress, Service exposure and existing TLS Secret | Existing controllers and TLS Secrets stay externally owned; controller exposure and public origin must agree |
| `aivision-secrets`, database password Secrets and application Secrets generated by `ensureSecrets` | Existing application/database Secret references and a separate first-install credential lifecycle | Reuse credentials on retry, upgrade and adoption. Missing credentials beside an existing database require restoration, never automatic regeneration |
| `STORAGE_CLASS`; observer data/redo/log requests and `signoz-metastore` PVC | Persistence class, requested sizes and retained-resource identity | Preserve PVC/PV bindings and metastore contents. Existing storage class changes are rejected; resizing or database-storage migration needs separate validation |
| Workload startup/readiness/liveness probes and termination grace in `base/` | Per-role probes and shutdown budgets | Start from the same endpoints, native commands and dependency semantics; readiness must not become initialization or dependency-sensitive liveness |
| Fixed replicas, Recreate strategies and serial Jobs in `base/` | Supported replica/update profile and bootstrap concurrency | Default to the evaluated single-instance profile. Exposing a value does not authorize extra SQLite writers, concurrent migrations or unverified diagnosis scale-out |
| Workload/Job resources, observer CR resources, gateway memory controls and upstream dependency exceptions | Per-role CPU/memory requests/limits and application memory controls | Validate the complete scheduling envelope and limiter headroom together; do not invent independent Chart defaults |
| `TIMEOUT`, Job deadlines, readiness gates and config/rollout annotations | Operation deadlines and deliberate rollout triggers | Account for each startup/bootstrap stage; do not assume one Helm timeout automatically matches the CLI's per-stage deadline |
| `aivision-runtime` organization ID from backend integration status | Bootstrap output consumed by diagnosis | Discover the existing organization; never make the private integration API key a value, ConfigMap entry or diagnostic output |

Current Kubernetes resource sizes, probes, replicas and strategies are fixed
manifest settings, not newly introduced CLI overrides. The CLI's saved
`config.json` holds non-secret client configuration; it is not database state
and is not a Helm release record. A future conversion must explicitly resolve
the current defaults, saved values and overrides rather than assuming a Chart
will read the operator's home directory.

## Installation, retries and upgrades

The future packaging must express these gates independently of a host-side
`aiv` process or manual edits to rendered YAML:

| Stage | Required outcome before dependents proceed |
| --- | --- |
| Namespace, credentials and dependencies | Validate ownership and capacity; reference or initialize stable Secrets; compatible cert-manager/OB Operator and admission webhooks are available |
| Database and tenant | OBCluster and OBTenant reach their required state; authenticated, idempotent database-init succeeds for all three application databases |
| Data backend, gateway and platform backend | Matching application images become Ready; platform entrypoint migrations complete before integration bootstrap |
| Integration bootstrap and organization discovery | Agent catalog and integration are configured idempotently; required integration status succeeds; the existing organization ID is published without exposing its private key |
| Diagnosis, frontend and public routes | Diagnosis consumes the discovered organization; public routes and authentication rejection checks pass; authenticated OTLP/query readback remains the final product acceptance |

Today `Cast` waits for each stage, recreates disposable Jobs with foreground
deletion, then executes backend integration status and writes the
`aivision-runtime` ConfigMap. Credential derivation, database immutability
checks, capacity checks and dependency ownership checks also run in the CLI.
These are explicit requirements for the future implementation, not capabilities
of the YAML files alone. In particular, organization publication needs an
in-cluster handoff or another independently supported mechanism. Its writer
must have only the permissions needed for the chosen output; the current
bootstrap Jobs have no Kubernetes API token. The design must not require a
prior CLI run to create credentials or runtime metadata.

Upgrade and retry must reuse Secrets, organization identity, metadata and PVCs,
serialize initialization attempts, and respect Recreate maintenance windows.
Failure must retain useful diagnostics and persistent state. Workload rollback
does not undo database migrations or integration changes; automatic rollback
and retry behavior must be tested explicitly before being offered. Hook
ordering, cleanup and release failure behavior remain implementation decisions,
but cannot skip these gates or regenerate identity on every render.

## Ownership and adoption

| Resource boundary | Current behavior | Required future migration/uninstall rule |
| --- | --- | --- |
| Product workloads, Services, Ingress routes, Jobs and ConfigMaps | Label `aivision.ob-labs.io/managed-by=aiv-kubernetes`; server-side apply manager `aiv-kubernetes`; foreign ownership is rejected | Use an explicit, validated ownership transfer for an existing installation. Do not relabel objects or force field conflicts as an implicit install step; only one deployment tool may reconcile it |
| Namespace and physical names | Dedicated namespace; compatible legacy workload names, selectors and DNS are retained | Keep the same identities during adoption. Neither a renamed component nor a release-name change may recreate persisted state; an existing namespace is not implicitly disposable |
| Database and tenant | Operator-owned children; OBCluster requests independent PVC lifecycle and OBTenant has `forceDelete: false` | Respect Operator ownership. Keep database resources, credentials and storage by default during a future application-only uninstall; define and separately validate explicit destructive removal |
| Data backend metastore | One `signoz-ob` writer on the `signoz-metastore` ReadWriteOnce PVC | Preserve the same claim and organization metadata. Any existing-claim/adoption option must prove single-writer ownership, retained-data access and uninstall behavior |
| Database/application Secrets | Stable master Secret and consistent derived credentials | Preserve them with retained data; removing the release must not make that data inaccessible by deleting or rotating its credentials |
| Shared CRDs/controllers, existing Ingress controllers/classes and external TLS/pull Secrets | Compatible installations are reused without modification; product Ingress routes remain managed by the product | Do not adopt, upgrade or delete another installation's shared resources as Chart side effects; record prerequisite ownership independently of the product release |

The CLI currently supports no Kubernetes `destroy` operation, and there is no
CLI-to-Helm migration procedure yet. Future adoption must inventory the actual
objects and owners, back up data and credential references, stop competing
reconciliation, and verify the preserved identities before switching ownership.
It must preserve the ability to recover on failure. Do not rely on an assumed
Helm retention annotation alone: Operator deletion behavior, resource ownership
and the storage class's reclaim policy must be tested together.

## Follow-up acceptance

The Chart follow-up must reuse the current deployment acceptance expectations:
fresh install, failed-bootstrap retry, image upgrade, authenticated telemetry
readback, Secret/organization/PVC preservation, probes, resource limits and
termination outcomes. Add real Helm install/upgrade/failure/adoption/uninstall
tests, including compatible shared dependencies and retained-data recovery.
Rendering success alone does not establish lifecycle support.

Resource/load and released-image qualification remain required for the current
deployment paths; deferring the Chart does not defer these gates. Helm runtime
validation belongs to the Chart follow-up.

# Kubernetes development and operational notes

[Deployment entry points](../README.md) · [简体中文](../zh-CN/kubernetes.md) | English

Requirements, deployment, verification and HTTPS configuration for an existing cluster are maintained in the [Kubernetes deployment documentation](https://aivision.mintlify.site/en/deployment/kubernetes). This page adds a local Linux kind setup and implementation limits. For parameters and operational commands, see the [aiv CLI reference](../../../aivision-cli/README.md#commands).

The authoritative product resources are [deploy/kubernetes/base/](../../../deploy/kubernetes/base/); upstream dependencies and licenses live in [dependencies/](../../../deploy/kubernetes/dependencies/). The CLI embedded directory is a compatibility copy generated by `make assets`. Install the product with `aiv cast --target kubernetes`. `aiv generate --target kubernetes` is a deprecated generic material conversion that omits the fixed product lifecycle and must not replace the installation command.

Helm is a committed future deployment path and currently unavailable. This delivery does not implement or publish a Chart or provide runnable Helm installation/upgrade commands. The [Helm roadmap](../../../deploy/kubernetes/helm-roadmap.md) maps current configuration to future values and records initialization, upgrade and persistent-resource ownership boundaries; it is not an executable values contract. Existing CLI deployments retain their Secrets, PVCs and identity and are not automatically adopted by Helm.

Roles follow the [shared naming map](../../../deploy/README.md#组件命名与兼容). New and old CLI selectors coexist; `app.kubernetes.io/component` labels are added while workload/Service/Job names, existing selectors, DNS, Secrets, namespace/state and PVCs are retained. Directory consolidation does not expand database support. New role interfaces require a CLI containing these changes; an older release version string does not establish support.

Static CI validates rendering and standard/pinned-CRD schemas; simulated-cluster tests check lifecycle contracts. Report those separately from live Kubernetes deployment. After an actual upgrade check organization identity, credentials, PVC bindings and telemetry capabilities supported by this target; Docker acceptance is not cluster acceptance.

The matching source lifecycle requires backend `/api/v1/ready`, diagnosis `/internal/readyz`, bounded shutdown, and gateway `/app/collector healthcheck --ready` image capabilities. The default native `healthcheck` provides only 2s local liveness; readiness runs three checks with 2s timeouts under a 10s Kubernetes budget. Source support in main is not proof that an image has been published with those capabilities. The [resource and lifecycle contract](../../../deploy/kubernetes/lifecycle.md) documents the single-replica Recreate profile, 3.4 CPU / 14Gi free-request preflight, per-application `TIMEOUT=30m`, and termination budgets. A 4 CPU / 16Gi cluster is an evaluation scheduling floor, not measured production capacity; readiness and static validation do not prove successful telemetry, load handling or an image upgrade.

## Local Linux kind cluster

Run this section only when creating a local test cluster. Prepare a running Docker daemon, `curl`, `tar`, `sha256sum`, `kubectl` and an [installed aiv CLI](https://aivision.mintlify.site/en/guides/install-cli). For an existing cluster, follow the published deployment guide and skip cluster creation.

Install kind (skip if already installed):

```bash
export PATH="$HOME/.local/bin:$PATH"; command -v kind >/dev/null || (set -eu; case "$(uname -m)" in x86_64|amd64) AIV_KIND_ARCH=amd64 ;; aarch64|arm64) AIV_KIND_ARCH=arm64 ;; *) echo 'Unsupported architecture' >&2; exit 1 ;; esac; AIV_KIND_TMP=$(mktemp -d); trap 'rm -rf -- "$AIV_KIND_TMP"' EXIT; cd "$AIV_KIND_TMP"; AIV_KIND_URL="https://github.com/kubernetes-sigs/kind/releases/download/v0.33.0/kind-linux-$AIV_KIND_ARCH"; curl -fLO "$AIV_KIND_URL"; curl -fLO "$AIV_KIND_URL.sha256sum"; sha256sum -c "kind-linux-$AIV_KIND_ARCH.sha256sum"; mkdir -p "$HOME/.local/bin"; install -m 755 "kind-linux-$AIV_KIND_ARCH" "$HOME/.local/bin/kind")
```

Set the data directory, adjusting the path as needed:

```bash
AIV_K8S_DATA="$HOME/aiv-k8s-data"
```

Create the `aivision` cluster:

```bash
(set -eu; case "$AIV_K8S_DATA" in *$'\n'*|*$'\r'*) echo 'Invalid data directory' >&2; exit 1 ;; esac; mkdir -p -- "$AIV_K8S_DATA"; AIV_K8S_DATA=$(cd -- "$AIV_K8S_DATA" && pwd -P); AIV_CGROUP=$(stat -fc %T /sys/fs/cgroup); printf "kind: Cluster\napiVersion: kind.x-k8s.io/v1alpha4\nnetworking:\n  apiServerAddress: 127.0.0.1\nnodes:\n- role: control-plane\n  extraMounts:\n  - hostPath: '%s'\n    containerPath: /var/local-path-provisioner\n  extraPortMappings:\n  - {containerPort: 30080, hostPort: 5174, listenAddress: 127.0.0.1}\n" "${AIV_K8S_DATA//\'/\'\'}" > aiv-kind.yaml; if [ "$AIV_CGROUP" != cgroup2fs ]; then printf 'containerdConfigPatches:\n- |-\n  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]\n    SystemdCgroup = false\nkubeadmConfigPatches:\n- |-\n  apiVersion: kubelet.config.k8s.io/v1beta1\n  kind: KubeletConfiguration\n  cgroupDriver: cgroupfs\n' >> aiv-kind.yaml; fi; KIND_EXPERIMENTAL_PROVIDER=docker kind create cluster --name aivision --image kindest/node:v1.34.11 --config aiv-kind.yaml --wait 5m)
```

Once the cluster is ready, follow the published deployment steps with context `kind-aivision` and namespace `aivision`. Set `PUBLIC_HOST: "127.0.0.1"` and `PUBLIC_PORT: "5174"` in the vars file. The `30080 → 5174` mapping above exposes both Web and OTLP HTTP.

## Entry point parameters and implementation limits

| Variable | Default / purpose |
| --- | --- |
| `PUBLIC_HOST` | `127.0.0.1`; an IP address or hostname reachable by external clients |
| `PUBLIC_PORT` | `5174`; the shared public port for Web and OTLP HTTP |
| `PUBLIC_SCHEME` | `http`; also accepts `https` |
| `INGRESS_CONTROLLER` | `managed` installs managed Traefik; `existing` reuses an installed Controller |
| `INGRESS_CLASS` | `aivision`; set this to the installed Controller's IngressClass when reusing it |
| `INGRESS_HTTP_NODE_PORT`, `INGRESS_HTTPS_NODE_PORT` | Managed entry point ports `30080`, `30443`; used only by the Controller Service |
| `INGRESS_TLS_SECRET` | Name of the same-namespace `kubernetes.io/tls` Secret required for HTTPS |

The managed Controller image is pinned to `traefik:v3.7.13` and watches only its own namespace; its class cannot be reused directly across namespaces. An existing Controller must watch the target namespace, and the cluster administrator configures its public address and ports. HTTP supports IP addresses; Ingress omits `host` when an IP is used.

For HTTPS domains, certificates and configuration, follow the published guide. When creating a new kind cluster with HTTPS, add a `containerPort: 30443` → `hostPort: 443` mapping to the configuration above and keep `30080 → 5174` for HTTP. Managed HTTPS routes bind only to the HTTPS entry point, without automatic HTTP redirection or certificate issuance.

## Updates, data and current limits

Update by repeating `aiv cast --target kubernetes ...` with the original context, namespace, and configuration. Single-replica applications use Recreate, so updates may interrupt service. Failed deployments retain resources without automatic rollback. The fixed path supports only `gauge`, `cast`, `status`, and `logs`; Docker-style `destroy` and `redeploy` are unavailable. Operators manage cluster backups and removal.

Do not reuse an entire Docker vars file. The current Kubernetes CLI supports only OceanBase CE managed by OB Operator, not bundled or external seekdb or external OceanBase. It does not accept `AIVISION_NATIVE_TRACE_HISTORY_START`, so native Langfuse v1 history reads cannot be enabled through this path. Use [Docker deployment](https://aivision.mintlify.site/en/deployment/docker) when those reads are required. SDK ingestion and v1 reads are separate capabilities.

Local management state defaults to `~/.aivision/deploy/kubernetes/`; data lives in cluster persistent volumes. YAML and local state alone are not a data backup. After opening the Web UI, verify collection and queries with an identifiable new Agent or SDK record.

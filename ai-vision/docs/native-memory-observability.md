# Native PowerContext memory observations

Memory observations scan recorded MCP calls and native PowerContext recall operations through the SigNoz `GET /api/v1/ai-vision/memory/operations` endpoint. This endpoint retains the existing organization, space, Agent and time filters and candidate pagination/byte/admission bounds. It does not change MCP discovery or turn HTTP calls into MCP tools.

## Supported evidence

The native adapter summarizes the two major operations, `prepare_context` and `capture_content_source`, from the normalized `powercontext.client` and `powercontext.server` instrumentation scopes. Each linked dependency/transport/application chain represents one business invocation. Prefer the SDK dependency boundary when present, then HTTP transport, then application; no server record or body is required. Scope binding, middleware wrappers and internal stages remain in the complete trace without increasing the summary call count. Repeated exports with the same trace/span identity do not multiply calls. A linked MCP operation or explicitly MCP-marked transport owns its nested native operations.

The selected business boundary supplies its actual outcome and duration. `powercontext.operation.outcome=success` is explicit success even when OTel status is UNSET; its own explicit error overrides success. A recovered lower transport attempt does not overwrite the SDK final outcome. Missing/cancelled/blocked outcomes remain unknown. Missing SDK duration is not replaced by a shorter server duration, and no OTel status is rewritten. New SDK boundaries and different operation boundaries remain separate, even when names or timestamps are close.

A linked `memory.search` stage contributes search evidence only when its mode establishes execution and it is not explicitly disabled/absent. A nonnegative integer result count supplies count-only hit evidence. Zero is a measured miss; missing/invalid counts are unknown, and unknown native search counts make the aggregate hit rate unknown. A skipped stage does not enter the search denominator. More than one linked search stage remains ambiguous: the invocation is visible but search metrics are not guessed.

The invocation duration measures the selected business boundary and retains fractional milliseconds. Native Trace aggregation uses the same original timestamps, preserving ISO microseconds and numeric nanoseconds; generic tool-duration attributes do not override this boundary. Capture is a separate business call and never enters the search denominator or creates saved-memory/inventory evidence. A search stage belongs only to its nearest preparation invocation, not every ancestor preparation. Search-duration fields use the linked search stage, when measured; the recall duration is not substituted for a missing stage duration. Memory entries and current inventory remain unavailable without separate recorded content/list evidence. HTTP argument summaries stay empty; raw queries and memory bodies are not required or captured by this adapter.

This initial support does not cover standalone native memory CRUD, orphan search stages, experience search, topic-memory search or background consolidation. Those require additional typed adapters rather than name-based guesses. Existing MCP result parsing remains unchanged.

## Trace and Run enhanced views

The Trace memory summary and standalone memory drawer share localized operation labels without changing the raw operation names, source IDs or API measurements. The standalone view uses operation vocabulary only for native calls; MCP calls retain tool vocabulary, and a mixed window names both. The server-level `callKinds` array records kinds from all canonical calls before name grouping and the recent-call limit, so preview filters and truncation cannot change this classification. Configuration catalogs and MCP tool definitions retain their original tool labels. Expanded records follow the neutral call-card and source-link styling used by MCP and Skill summaries. The standalone page retains window-wide totals and percentiles even when its recent-call preview is limited; Trace totals cover the loaded trace and sum the selected business durations, rather than displaying a window percentile. Expand the engine row to select preparation or completed-turn capture and navigate to its SDK Run. Linked SDK, HTTP, server and search stages do not become additional calls; the complete left-side chain remains available. Explicit MCP identity owns both the current span and nested native operations, including a span carrying both native and MCP metadata.

Chain, Timeline and Graph share typed PowerContext operation icons and layer labels. The Run view covers recall, scope binding, context preparation, capture and supported search/build/lock stages when their instrumentation scope and operation/unit identify them. Display-only scope binding, experience search and topic-memory search do not enter business call counts or the atomic-memory search metrics. Capture contributes one business call, independently of recall/search metrics. Original names remain searchable and available in tooltips and raw details.

Run detail counts use unambiguous, successful native evidence along actual same-trace parent IDs. A search count links to its reporting stage. Missing, failed, skipped or ambiguous counts remain unknown; a measured zero remains zero. Capture `source_count` is a reported input-source count, not a count of newly saved memories. Child navigation starts with five operations and supports more/all/collapse. The parent-recall action is shown only for a reported ancestor, not a nearby sibling or completed-turn capture.

SDK scope binding and context preparation details explain their role and expose already reported operation metadata by default. When their own IO is absent, a separate **Related recall reference** section can reuse the nearest typed middleware recall's recorded input and scope ID, with source navigation. Context preparation can also reference that recall's recorded context when it is the sole successful SDK preparation under that recall and no PowerContext ancestor reports failure, cancellation or blocking. Scope binding never borrows the prepared context. Conflicting scope IDs, missing parents, cycles and cross-trace records do not establish a reference; multiple preparations cannot attribute a final recall context to one attempt. Own IO remains authoritative, reference content is explicitly attributed, and raw attributes, copy/export ownership and metric counts remain unchanged. This presentation reuses loaded evidence without additional producer capture, requests or database writes; missing or masked content is not reconstructed.

Reference input and output retain their respective reported truncation flags, with an explicit localized **Content truncated** badge for boolean `true` or string `"true"`. The badge does not change the received value used for display/copy or the operation's status. Missing/false flags do not invent truncation; a parent's flag is not applied to the step's own IO.

The [truncated reference example](assets/powercontext-sdk-reference/after-truncated-prepare.webp) uses synthetic 16 KiB input/output prefixes with their respective true flags. It verifies that both source-level truncation notices remain visible alongside the bounded text preview.

Opt-in Middleware recall content and actual model system input can display complete supported PowerContext V1 memory records as readable historical reference, with citation family, artifact ID and revision. Current instructions take precedence. The view does not establish that a memory is correct or that the model used it to reason. Unknown protocol versions, malformed/mixed payloads and uncertain truncation fall back to the existing typed renderer. Generic user text cannot claim this projection. Raw mode and copy retain the received SDK envelope, quotes and escaped newlines; attributes and resources remain accessible. Missing or privacy-masked text is not reconstructed.

## Delivery and compatibility

Upgrade the SigNoz data plane with the companion native-memory endpoint before upgrading the platform backend/frontend. An older data plane returns an explicit unsupported-capability error instead of a successful empty native-memory scan. The Langfuse data source itself remains explicitly unsupported for this native scan; Langfuse SDK spans collected into SigNoz are supported.

No database migration, second exporter or MCP endpoint is required for the native scan. Instrumentation scope must survive storage and readback; the companion data plane normalizes the standard stored scope columns instead of requiring fabricated application attributes. The native recall spans remain in the Agent trace, and Memory Observability aggregates the same records. Imported MCP configuration controls metadata/catalog discovery; it is not a subscription to native HTTP telemetry or a service-health probe.

Complete producer-side phase parentage is a separate integration contract. The tested candidate for [PowerContext #2517](https://github.com/oceanbase/powercontext/pull/2517) needs its matching updated core for default-filter SDK visibility. With the tested asynchronous LangChain/Langfuse versions, public inline callback configuration and a per-invocation OpenTelemetry scope boundary establish the intended recall → model → capture phase relationship. Cancellation generation cleanup and cancellation metadata additionally used local changes in the owning LangChain/Langfuse dependencies. These are validation prerequisites, not changes or bundled dependencies of this AI Vision PR; do not describe #2517 alone or a stock dependency install as the complete cancellation fix.

## Verification boundaries

Regression coverage includes MCP behavior and direct-span ownership, scope propagation, unsupported providers, canonical layer selection, status precedence, count-only/zero/missing results, skipped searches, and trace links. Display tests also cover metadata classification, explicit MCP/Skill/Decision priority, real-parent navigation, bounded child controls, strict content fallback, exact raw copy, localized search and deep Timeline label width. No dependency or lockfile upgrade is required.

Validation receipts identify the actual tested source, paired data plane, commands and screenshots. Relevant checks include backend native-memory/provider regressions, frontend MCP/memory and locale regressions, changed-file ESLint, typecheck, build, targeted Python Ruff and whitespace checks. Window-wide classification covers native-only, MCP-only, mixed kinds, name collisions and capped recent history. Local source checks remain distinct from hosted CI and deployment qualification.

A successful locally stored official `FakeMessagesListChatModel` trace contains 24 spans, including 19 explicitly identified native PowerContext spans, two business calls (preparation and completed-turn capture), with one reported atomic-memory hit. The query lacks the seeded marker; actual model system input contains the recalled content. The model response is preset, so its text is not inference-quality evidence. Actual local browser checks cover Trace → expand the two major operation records → select the corresponding SDK Run → parent recall/reporting search stage when available, capture source count, raw mode, Chain/Timeline/Graph and selected theme/locale layouts. All 24 stored span records remain exactly equal to the original readback; this UI validation reuses that execution without rewriting or re-ingesting telemetry.

Earlier read-only replay of two actual stored HTTP-backed Agent traces yielded 1/4 invocations from 17/62 spans with unknown search execution. Real SeekDB fixture validation uses uniquely named temporary tables and leaves existing telemetry unchanged. None of these results establishes a production rollout, cross-browser coverage or a released producer cancellation fix.
